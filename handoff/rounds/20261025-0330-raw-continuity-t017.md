## 3. 本轮实现与理由
| 文件/模块 | 改了什么 | 为什么这样改 | 替代方案/取舍 | 影响与回滚 |
| --- | --- | --- | --- | --- |
| `scripts/verify-host-continuity.mjs` | 移除 `WorkbenchContextManager` 客户端注入与本地 `history` 伪造，直接发送 raw 用户输入字符串至 `/api/workbench/chat/send` | 测试驱动不能代替产品完成多轮指代组装；必须由工作台服务端拉取 SQLite 历史并投影 | 无替代；必须让服务端自我闭环 | 仅改验证探针，不影响业务代码 |
| `src/host/services/host-session.ts` | 1. `HostTurnStatus` 扩充 `awaiting_input` 与 `stopped`；<br>2. `sendAndCollect` 识别 `agentStatus === 'awaiting_input'` 并即时提取问题文本返回；<br>3. 公开 `eventsOf` 与静态方法 `extractAssistantMessages` | 宿主提问/确认需要快速感知，不能挂起 180s 直至超时 | 若只靠轮询超时，用户体验严重滞后且无法区分故障与等待输入 | 向后兼容既有接口 |
| `src/host/services/host-tracker.ts`（新增） | 实现 `HostSessionTracker`：<br>1. 会话生命周期状态持久化（`assistant_state.memory_index_json.pendingHostTurn`）；<br>2. 提问与等待输入投影；<br>3. 后台轮询跟踪晚到正文并写入 SQLite `chat_messages` 及 Outbox；<br>4. 重启核对宿主状态（“重启无双发”，绝不重发旧 prompt）；<br>5. 停止联动调用 `bridge.cancel` 与停稳核验 | 解决 T-017 核心问题：主助理回合 HTTP 结束后后台仍可能产出成果或提问；必须统一在主入口显示与作答，停止时必须统一步调 | 若直接修改 TaskScheduler 会破坏纯 Worker 任务与对话会话的职责隔离；采用 Tracker + LocalProvider 聚合最干净 | 纯增量模块，无破坏性改动 |
| `src/host/services/domain.ts` | `saveChatMessage` 保存时校验 `intentId`，若指定了不存在的外键 ID 则安全降级为 `null` | 防止因意图 ID 孤儿或测试合成 ID 导致 SQLite 787 外键约束崩溃而丢失关键聊天消息 | 若强制必须存在意图，偶发系统事件或独立提问将无法保存消息 | 提升系统鲁棒性，保护关键聊天记录 |
| `src/providers/local.ts` | `LocalProvider` 引入 `HostSessionTracker`，将宿主 pending 状态合并到 `getControlSnapshot`，并在 `stopRun`、`stopIntent`、`stopAll` 中深度联动宿主取消 | 控制条与停止 API 必须统一代表整个工作台的权威执行状态（含后台任务与宿主会话） | 若仅在路由层处理，远程 RemoteProvider 联调无法对等消费控制契约 | 保持 Provider 单一控制契约 |
| `src/index.ts` | 1. 实例化 `HostSessionTracker` 并注入 `LocalProvider`；<br>2. 在 `hostAssistantTurn` 中深度接线 tracker 记录与后台轮询；<br>3. `/api/workbench/chat/send` 识别 `awaiting_input`：当存在待决提问时，用户输入直接路由为答复，无需切换会话；用户说“停止”时统一中断 | 用户在单一主入口即可完成提问作答与停止，主回合结束后控制条依然可用 | 若要求用户切换后台 session，严重违背单一主助理入口的核心产品原则 | 路由逻辑平滑升级 |
| `tests/host-pending-t017.test.mjs`（新增） | 覆盖 T-017 的 5 个专项用例：提问识别投影、主入口作答、停止联动、晚到正文后台捕获、重启无双发核验 | 确保 T-017 全场景具备机械级回归与变异防护 | 无 | 自动化测试套件扩充至 111 项 |
