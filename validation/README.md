## 当前可以运行什么

在仓库根目录运行：

```text
node validation/check-catalog.mjs
```

只使用Node内置库；不调用模型、不启动DSH、不连接真实项目、不写报告或数据库。检查144个ID、14组计数、26个不变量引用、动作协议和字段完整性。输出CATALOG_VALID只说明目录结构有效，不代表语义完整、断言已实现或产品通过。

## 场景如何变成自动测试

每条case包含fixtureId、独立variantId、用户输入/UI动作/故障、预期及不变量。动作中的中文名称和fault标识是施工规格，需明确映射到测试驱动；不能把它们直接当成已经存在的DSH接口。

后续Agent需要实现：不同variant的真实准备动作、对产品的操作、独立oracle、超时策略和证据采集。任何未实现项应失败或明确BLOCKED，禁止通用空实现返回成功。语义场景的确定性L1使用规范化意图，真实中文理解另在L2调用真实模型检查。

默认deadlineMs仅是规格占位上限；长工具、安装、性能与恢复场景必须在driver中声明合理时间预算。不能靠延长等待掩盖永久挂起。

requiredLevels表示计划要求取得的各层证据；同一case在L1通过不能顶替L2/L3。L4是少量真人试用，不强求每天重做全部场景。

## 分阶段推进

144条是完整回归目标，不要求首轮一次实现所有扩展功能。先接通真实主助理、实际执行、任务回写、独立停止和恢复闭环。检查点暂停、跨设备、升级迁移等能力按发布范围逐步接入；未提供的能力应明确标为未实现/阻塞并在界面禁用，不能宣称已通过。

P0/P1用于相应能力启用后的严重程度分级；首轮试用必须覆盖自动化计划第9节的底线。任何已启用功能的错范围控制、假停止、重复副作用或丢输入都阻止日用试用。

## 结果纪律

此目录固定为SPECIFICATION_ONLY，全部case固定PLANNED。执行报告另存，包含层级、版本、trace与独立证据，不能把计划目录改成PASS。不得把私人任务、用户真实文件、密钥或原始聊天提交到公开仓库。
